# 화면 설계 — 학생 상세

[CLAUDE.md](../../CLAUDE.md) 화면 흐름의 "학생 상세" 단계 상세 설계 (P2 범위). [출석 입력 화면](attendance-input.md)에서 학생 이름을 탭하면 진입한다. 이 화면을 구현할 때는 이 문서를 스펙으로 따른다.

## 화면 목적

한 학생의 **프로필 메모**(`student_notes` — 날짜 무관, 지속적 특이사항)와 **출석 이력**(`attendance` — 과거 기록 조회 + 인라인 수정)을 한 화면에서 다룬다. 반별 월간 통계·출석률 같은 집계 리포트는 P3 범위이며 이 화면에 넣지 않는다 — 여기서는 "단순 합계"까지만 다룬다(아래 참고).

## 레이아웃

```
┌─────────────────────────────────────┐
│ ←  김민수                             │  ← 상단바: 뒤로가기 + 이름
│    고3 · 중등부 · (비활성)            │  ← 학년 · 반, 비활성일 때만 뱃지
├─────────────────────────────────────┤
│ 프로필 메모                           │
│ ┌───────────────────────────────┐   │
│ │ 새 메모 추가...            [등록]│   │  ← 교사/관리자만 노출
│ └───────────────────────────────┘   │
│ 2026.08.15 · 박교사                  │
│  알레르기 있음 (땅콩)                 │
│ 2026.03.02 · 김관리자                │
│  전학 옴                             │
├─────────────────────────────────────┤
│ 출석 이력            2026년 ▾         │  ← 연도 필터
│ 출석 20 · 지각 2 · 결석 1 · 공예배 1  │  ← 단순 합계 (선택된 연도 기준)
├─────────────────────────────────────┤
│ 2026.09.20(일)                        │
│ [출석][지각][결석][공예배] 💬         │  ← 인라인 수정
├─────────────────────────────────────┤
│ 2026.09.13(일)                        │
│ [출석][지각][결석][공예배] 💬         │
│  └ 코멘트: 지각 이유                  │
├─────────────────────────────────────┤
│ ...                                  │
└─────────────────────────────────────┘
```

뒤로가기(←)는 출석 입력 화면으로 돌아가되, 떠나기 전 컨텍스트(반/날짜)를 유지한다.

## 상단바

- 학생 이름, 현재 `grade`(없으면 "미지정") · 현재 `classes.name`.
- `students.is_active = false`인 학생은 옆에 "비활성" 뱃지를 표시한다. 출석 입력 화면의 학생 리스트에서는 비활성 학생을 완전히 제외하지만, 이 화면은 **과거 기록 열람** 목적이므로 비활성 학생도 조회 가능해야 한다(전출/졸업한 학생의 지난 출석 이력도 남아 있어야 함) — 다만 현재는 이 화면으로 들어오는 진입 경로가 "출석 입력 화면에서 이름 탭"뿐이라 비활성 학생 진입 경로는 아직 없다. 학생 마스터 관리 화면(P3)에서 진입 경로가 생기기 전까지는 실사용에 노출되지 않는 케이스지만, 화면 자체는 비활성 학생 데이터를 받아도 정상 동작하도록 만든다.

## 프로필 메모 (`student_notes`)

- **수정은 지원하지 않고 삭제만 지원**한다 — `student_notes` 테이블에 `updated_at` 컬럼이 없고 "지속 특이사항이 시간에 따라 쌓이는 기록"이라는 취지상 수정 UI는 두지 않는다. 잘못 쓴 메모는 삭제 후 다시 등록한다. 삭제는 확인 대화상자를 거치는 하드 삭제이며(되돌릴 수 없음), 작성자와 무관하게 쓰기 권한이 있는 교사·관리자면 누구나 지울 수 있다(과거 기록 수정 잠금 없음 원칙과 동일한 기조). DB 권한은 `0005_student_notes_delete.sql`에서 `delete`를 GRANT하고, 행 단위 허용 범위는 기존 RLS `student_notes_write`가 결정한다.
- 정렬: `created_at` 내림차순(최신이 위).
- 항목 표시: 작성일, 작성자 이름(`teachers.name` 조인), 내용.
- 입력창은 **교사·관리자에게만 노출**한다(목사님은 조회 전용). RLS(`student_notes_write`)가 DB 레벨에서도 막아주지만, 프론트에서도 role 기준으로 입력창 자체를 렌더링하지 않는다.

### 데이터 계약
`app/actions/students.ts` → `addStudentNote`
```ts
type AddStudentNoteParams = { studentId: string; note: string };
```
insert만 한다.

`app/actions/students.ts` → `deleteStudentNote`
```ts
type DeleteStudentNoteParams = { noteId: string };
```
RLS로 막힌 행은 에러 없이 0건 삭제로 끝나므로, 삭제된 행이 없으면 실패로 처리한다. 수정(update) 액션은 만들지 않는다.

## 출석 이력 (`attendance`)

### 정렬 & 범위
- 날짜 내림차순(최신이 위).
- **실제로 `attendance` 레코드가 존재하는 날짜만 나열한다** — 출석 입력 화면의 "미체크" 개념(그 날짜를 콕 집어 볼 때만 의미 있음)과 달리, 이 화면은 과거 전체를 훑어보는 용도라 기록 없는 날짜까지 나열하면 무한정 늘어나 비현실적이다. 즉 이 화면의 "결석"은 교사가 실제로 `결석`을 눌러 저장한 기록만 의미하며, 출석 입력 화면의 "미체크=결석 인지" 규칙과는 별개 문맥이다.
- **연도 필터**: 상단에 연도 드롭다운(기본값: 가장 최근 기록이 있는 연도). 연도를 바꾸면 그 연도 범위(`date >= YYYY-01-01 and < (YYYY+1)-01-01`)만 다시 조회한다. 데이터 규모가 작아(주 1회 기록) 무한 스크롤 대신 이 방식으로 충분하다.

### 단순 합계
- 선택된 연도 범위 안에서 로드된 이력을 클라이언트에서 그대로 합산해 상태별 횟수를 보여준다(`출석 20 · 지각 2 · 결석 1 · 공예배 1`).
- 월별 집계, 출석률(%), 반 간 비교 같은 것은 포함하지 않는다 — 그런 건 P3 통계 작업 범위다. 이 합계는 별도 쿼리 없이 이미 불러온 리스트를 더하는 것뿐이라 추가 DB 부담이 없다.

### 인라인 수정
과거 기록 수정에 잠금이 없다는 원칙(CLAUDE.md 권한 모델)에 따라, 이 화면에서도 각 이력 행의 상태 버튼을 바로 눌러 수정할 수 있다.

- **출석 입력 화면과 동일한 컴포넌트/저장 로직을 재사용**한다 — 상태 버튼 UI, 색상 규칙, 코멘트 펼침 동작, `saveAttendanceStatus`/`saveAttendanceComment` 서버 액션([attendance-input.md](attendance-input.md#저장-appactionsattendancets--saveattendancestatus--saveattendancecomment) 참고) 그대로 호출한다. 이 화면 전용 저장 액션을 새로 만들지 않는다(중복 구현 금지 원칙).
- 각 이력 행은 이미 `studentId`/`classId`(그 날짜 시점의 `attendance.class_id`)/`date`/`status`/`comment`를 갖고 있으므로, 상태 버튼 탭 → `saveAttendanceStatus({ studentId, classId, date, status })` 그대로 호출하면 된다.
- "코멘트는 상태가 선택된 이후에만 입력 가능" 제약도 동일하게 적용된다(이력 화면에서는 이미 상태가 있는 행만 나열되므로 사실상 항상 코멘트 입력이 가능하다).
- 낙관적 UI, 실패 시 롤백/토스트도 출석 입력 화면과 동일한 정책을 따른다.

## 데이터 계약 — 조회

`app/actions/students.ts` → `getStudentDetail`
```ts
type GetStudentDetailParams = { studentId: string; year?: number }; // year 생략 시 최신 기록 연도

type StudentDetailResult = {
  student: {
    name: string;
    grade: '중1' | '중2' | '중3' | '고1' | '고2' | '고3' | null;
    className: string;
    isActive: boolean;
  };
  availableYears: number[]; // 이 학생의 기록이 존재하는 연도 목록(드롭다운용)
  notes: { id: string; note: string; authorName: string; createdAt: string }[];
  attendanceHistory: {
    date: string;
    classId: string; // 인라인 수정 시 saveAttendanceStatus에 그대로 전달
    status: '출석' | '지각' | '결석' | '공예배';
    comment: string | null;
  }[];
  summary: { 출석: number; 지각: number; 결석: number; 공예배: number };
};
```

- 내부 쿼리는 `lib/db/students.ts`(학생 기본 정보 + `student_notes`)와 `lib/db/attendance.ts`(연도 범위 이력 + 합계)로 분리한다.
- `recorded_by`, `last_modified_*` 등 감사 필드는 이 화면에 내려주지 않는다.

## 권한

- **조회**(학생 정보, 메모, 이력): 관리자 / 교사(접근 가능한 반 범위) / 목사님 모두 가능 — 기존 `students_select`, `student_notes_select`, `attendance_select` RLS 정책 그대로 적용.
- **쓰기**(메모 추가·삭제, 출석 인라인 수정): 관리자 / 교사만. 목사님은 `student_notes_write`, `attendance_write` RLS에서 이미 제외되어 있으므로, 프론트에서도 role 기준으로 메모 입력창과 상태 버튼을 비활성화(또는 읽기 전용 텍스트로 대체)한다.

## 에러/로딩 상태

- 최초 조회 로딩: 메모/이력 영역 각각 스켈레톤.
- 조회 실패: 재시도 버튼 + 에러 메시지.
- 메모 등록/상태 수정 실패: 토스트로 에러 표시, 실패한 항목은 이전 상태로 롤백.

## 이 화면에서 다루지 않는 것 (범위 밖)

- 월별/반별 통계, 출석률, 통계 리포트 엑셀 내보내기 — P3.
- `student_notes` 수정 — 삭제 후 재등록으로 대체(삭제는 지원).
- 비활성 학생으로의 진입 경로(학생 마스터 관리 화면) — P3.
